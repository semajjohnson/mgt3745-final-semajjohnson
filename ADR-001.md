# ADR-001: Build the pool as a hand-written browser page instead of on a streaming platform's API

Status: **Superseded by [ADR-002](ADR-002.md)** on 2026-09-30. Kept because the Gate below is the decision this project was founded on, and because ADR-002 only replaced where entries are stored, not the choice to build rather than buy.
Date: 2026-09-22

## Context

The pool must show a source name on every item (A5 in [FEATURES.md](../context/FEATURES.md)), and the spec says it holds playable tracks only.

HW2 assumed Spotify. Two things undid that. One of my two interviewees uses Apple Music, and the two platforms store incompatible track identifiers, so a pool built on either is a pool half my users cannot fill. Spotify's 2026 terms also require the app owner to hold Premium, cap apps at five users, and have removed endpoints twice this year.

The budget is zero. I reworded that constraint to "no new spending," because I already pay for Premium personally, which makes the marginal cost zero but quietly makes a personal subscription a dependency of the app. That rewording is recorded here rather than buried in the constraint, because it is the kind of thing that looks free and is not.

I cannot yet comfortably read client or server code I did not write, and the deadline is one week. That weighs directly against delegating anything I would have to approve unread.

## The Gate

**Feature under decision:** the pool itself. A list where every track carries the name of the person it came from, and the list survives a reload.

**Hard constraints.** An option failing either is rejected before scoring. All three passed.

1. No new spending.
2. Runs from a fresh Codespace with Live Server, so every grader and reviewer sees the same environment.

Serving both Spotify and Apple Music users was considered as a hard constraint and deliberately demoted to a scored criterion. As a constraint it would have rejected both Spotify-based options before scoring and left the comparison with nothing to compare.

| Criterion | Weight | Build: hand-written page | Buy: Spotify Web API | Delegate: AI builder |
|---|---:|---:|---:|---:|
| Cost to start | 3 | 5 (15) | 3 (9) | 3 (9) |
| Cost to maintain | 2 | 5 (10) | 1 (2) | 1 (2) |
| Time to working | 3 | 5 (15) | 2 (6) | 3 (9) |
| Inspectability | 4 | 4 (16) | 1 (4) | 1 (4) |
| Switching cost | 4 | 5 (20) | 1 (4) | 1 (4) |
| Fit to spec | 5 | 3 (15) | 4 (20) | 3 (15) |
| **Weighted total** (max 105) | | **91** | **45** | **43** |

Buy scores highest of the three on fit to spec, and loses anyway. That is the Gate working: a platform API is the only option that can guarantee a track is real and playable, and it is beaten by everything else at once.

## Options considered

| Option | For | Against |
|---|---|---|
| **Build:** hand-written HTML, CSS, and JavaScript with `localStorage`; tracks and source names typed by hand | No platform dependency, so it works for users on any service. I can read and explain every line, which matters because I will have to inspect delegated code later. Plain JSON, so moving it later is cheap. Working this week. | Typed text accepts typos, so it cannot guarantee a playable track, which breaks a stated non-goal. Does not implement F1, automatic capture, which is a Must-be row. |
| **Buy:** Spotify Web API, storing real Spotify track IDs with a source name | Guarantees the track exists and is playable. Removes manual entry, which is the thing Profile A will not do. | Requires Premium, caps at five users, and endpoints have been removed twice this year. Excludes my Apple Music interviewee outright. Leaving means redesign, not export. |
| **Delegate:** Copilot or a coding agent builds the Spotify integration and I inspect the result | Fastest path to a platform integration I could not write myself. | I cannot yet audit code I did not write, so "I inspect the result" is a claim I cannot honor. Inherits every Spotify constraint above and adds code I do not understand. |

## Decision

Build the pool by hand as three static files saving to `localStorage`, with a source name required before any item is saved.

This slice reads no listening data, so it needs no platform API at all. Automatic capture (F1 and F3) will need one eventually, and Spotify remains the likely candidate, though it offers no public access to shared listening sessions, which is the whole reason F1 and F3 are deferred rather than scheduled.

The Gate and the course's required hand-build agree here. Worth noting that had the Gate chosen Delegate, the hand build would still have been required, so I could inspect delegated code later.

## Consequences

**What this makes worse.** The pool cannot guarantee a playable track, because typed text accepts typos, and that breaks a non-goal the spec states plainly. It does not implement F1, automatic capture, which is classified Must-be. Manual entry asks Profile A, the Casual Listener, to do admin work the research says they will not do. And data lives in one browser with no sync, so the pool does not survive a cleared cache or follow a user to a second device.

That last consequence is the one that ended this ADR three weeks later.

**What it buys.** A working page I can read and verify inside a week, usable by listeners on any platform, storing plain JSON that is cheap to move.

## Reversal trigger

Revisit when a streaming platform opens shared-listening data to small developers, or when the course introduces a database.

**The second trigger fired on 2026-09-30.** See [ADR-002](ADR-002.md).
