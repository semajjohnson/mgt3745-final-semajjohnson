# ADR-002: Move pool entries from browser storage to a Cloudflare Worker and D1 database

Status: **Accepted.** Supersedes [ADR-001](ADR-001.md). This is the architecture the project currently runs on.
Date: 2026-09-30. Gate scores reconstructed 2026-11-05; see the note below the table.

## Context

ADR-001 chose `localStorage` and named the two triggers that would end it: the pool needing to exist on more than one device, and a database arriving in the course. Both became true in the same week.

`localStorage` could never deliver the behavior the spec always implied. A pool that vanishes with a cleared cache, and that does not follow a listener from their laptop to their phone, is not a pool. ADR-001 recorded that as a known cost rather than discovering it later, which is why this decision is a scheduled replacement and not a rescue.

The Gate below scored Build 80, Buy 55, and Delegate 46, with switching cost scored from the move I had already made rather than from an estimate.

### The crossing

**What crosses:** every track name and, more consequentially, the name of a real person a user was recommended music by, plus a dismissal flag and a timestamp. Cloudflare also receives request metadata I did not choose to send: IP address, user agent, timing, and the paths called.

**To whom:** Cloudflare, through Workers and D1.

**Under what terms:** a free personal account, with no contract and no data-processing agreement. Cloudflare is accountable only for running the code I deployed.

**Who is accountable:** me, for everything that gets sent. The people named in the table never consented to being recorded, and there is no mechanism for them to ask to be removed. Every row is in [TOOLS.md](../context/TOOLS.md).

> **On these numbers.** The decision was made on 2026-09-30, but the per-criterion scores were never written down at the time; the table sat blank in every commit from the initial template onward, while the surrounding prose claimed totals of 87, 54, and 40. Rather than carry figures with nothing behind them, I rescored all three options on 2026-11-05 against the same anchors ADR-001 used, and replaced the remembered totals with these. Buy and Delegate landed within a point or six of what I remembered. Build landed at 80 rather than 87, which I take to mean the original figure was generous. The decision is unchanged either way: Build wins by 25 points.

**Where the scoring is worth reading closely.**

Build scores *lower* than my hand-written page did on inspectability, 3 against ADR-001's 4. That is the honest direction. A Worker plus a SQL schema is harder for me to read than three static files I typed myself, and pretending otherwise would hide the main cost of this decision.

Build scores *higher* on fit to spec than anything in ADR-001, a 5. Acceptance row A5 asks that every item carry a source name, and the spec's non-goals are about not recommending and not ranking. Moving storage violates none of them, and it fixes the one thing `localStorage` could never do. The offline regression and the single-user problem below are consequences of this decision, not failures against the spec.

Switching cost at 4 is the one score my own Prediction Stake in [SOURCING-AUDIT.md](SOURCING-AUDIT.md) bets against. I have never run the export that this score assumes is easy.

## Options considered

| Option | For | Against |
|---|---|---|
| **Build:** my own Worker and D1 database, deployed with wrangler | One vendor, no new service, and I control every endpoint. Validation moves server-side where it cannot be bypassed. Rows are plain SQL data, so leaving is an export and one rewrite. | I own account security and schema design. Harder for me to read than the page it replaced. D1 is a vendor machine holding the names of real people under a free account. |
| **Buy:** a hosted backend service | Less to build and less to maintain, and faster to something running. | A second vendor holding the same sensitive rows, outside the stack the course uses. I cannot read their backend at all, and leaving means export by hand. |
| **Delegate:** let an AI builder generate and host the backend | Fastest route to a working backend I could not write myself. | Code I did not write, on hosting I do not control, holding the same data. ADR-001 already established that I cannot audit what I did not write, and nothing had changed in eight days. |

## Decision

Pool storage moves out of the browser into a D1 database reached through a Worker I deploy.

- `GET /entries` returns undismissed rows
- `POST /entries` validates and inserts one row per track-and-person pair
- `POST /entries/:id/dismiss` marks a row so it cannot return

Deployed with wrangler to `https://mgt3745-hw4.semajjohnson.workers.dev`, backed by a D1 database named `mgt3745-entries`.

## Consequences

**What this makes worse.**

The page no longer works offline at all, where before it worked entirely offline. A listener on a subway now sees an error instead of their pool. That is a straight regression for Profile A, the Casual Listener, who listens while doing something else and is exactly the person most likely to be underground.

Testing got harder in the same direction. The 500 path exists in the Worker but cannot be triggered on a deployed instance without shipping broken code, which is why that verification row still reads CANNOT TEST YET.

I also now read my own storage layer less fluently than I read the page it replaced, which the Gate records as a drop from 4 to 3 on inspectability. Every future bug in `worker.js` costs me more to find than the same bug would have cost in `app.js`.

And the table holds the names of real people on a vendor's machine under a free account, which is a responsibility `localStorage` never created. Nobody named in it agreed to be there.

**What this decision fails to do.** It does not make the pool multi-user. One D1 table is shared by every page that calls the Worker, so two people using it would see each other's entries with no notion of ownership. The pool is single-user by design and by accident at the same time, which is the worse of the two ways to be single-user.

**What it buys.** The pool survives a cleared cache and appears in any browser, which is the behavior the spec always implied. Validation moved to the server where it cannot be bypassed, and A7 became implementable and testable for the first time.

## Reversal trigger

Revisit when any one of these happens:

- A second person uses the pool. Every assumption above is single-writer, and two writers on one D1 table is the next ADR.
- The free tier stops covering it, whether through D1 row limits or Worker request limits.
- Anyone named in the table asks to be removed, which I currently have no way to handle.
- The export this Gate scored a 4 on turns out not to work. That is the Prediction Stake in [SOURCING-AUDIT.md](SOURCING-AUDIT.md), and if it resolves against me, switching cost drops and this Gate gets rerun.

The third trigger is the one I am least prepared for and the most likely to be asked about.
